# ADR-001: SPA Architecture for the Front-End

---

## author: Molid
domain: front-end
status-validated: 2026-07-07

## Context

The TrocSkillHub front-end must provide a smooth interface allowing users to navigate between several pages: home page, authentication, profile, profile search, skills consultation and management of personal information.

The application communicates with a separate back-end exposed as a REST API. The front-end is therefore mainly responsible for display, client-side navigation, user state management and calls to back-end services.

The project also requires a simple front-end deployment as static files, hosted on an OVHcloud web server, with HTTPS configuration and routing adapted to the application's pages.

## Decision

I chose a **SPA** (*Single Page Application*) architecture for the TrocSkillHub front-end because React is particularly suitable for this type of architecture. It allows building a dynamic client-side interface based on reusable components.

In the case of TrocSkillHub, the user can navigate between several views without a full page reload, which improves the fluidity of the user experience.

React also integrates well with tools such as React Router for client-side navigation and libraries such as TanStack Query for API calls and data caching.

## Alternatives Considered

Classic multi-page application: each page change reloads a new page from the server. This approach is easier to understand and can be suitable for mostly static websites, but it is less fluid for an interactive application like TrocSkillHub.

Server-side rendering with SSR: a solution such as Next.js would allow pages to be generated on the server side, with potential benefits for search engine optimization and initial loading. However, it adds an additional infrastructure and configuration layer, while the project already relies on a separate back-end and a REST API.

Monolithic full-stack application: the front-end could have been integrated directly into the Spring Boot back-end project with server-side templates. This solution can sometimes simplify deployment, but it reduces the separation between the interface and the API, and makes the front-end less independent.

## Consequences

Positive: the user experience is smoother because page changes do not require a full reload. The front-end can be developed, tested and deployed separately from the back-end. Deployment is simple because the application generated by Vite produces static files that can be hosted on OVHcloud. This architecture is also consistent with the use of React, TypeScript, TanStack Query and React Router.

Negative: the initial loading can be heavier than a simple HTML page because the browser must load the application's JavaScript. Search engine optimization can also be less efficient than with an SSR architecture, because the content is mainly generated on the client side. The web server must also be correctly configured to redirect routes to `index.html`; otherwise, direct access to an internal route may cause a 404 error.

What could reopen the decision: if the project requires significant search engine optimization on public pages, if initial loading performance becomes insufficient, or if the application needs to expose a lot of indexable content without authentication. In that case, a migration to an SSR architecture with Next.js could be considered.

# ADR-002: React for the Front-End

---

## author: Molid
domain: front-end
status-validated: 2026-07-07

## Context

The TrocSkillHub project requires a dynamic, responsive and maintainable web interface. The application includes several views: authentication, user profile, profile search, skills display and interactions with the back-end API. The front-end must therefore be clearly organized, with reusable components, a separation between display and application logic, and efficient client-side navigation management.

The project is also part of a modern SPA (*Single Page Application*) web application approach, where the user navigates between the different views without a full page reload.

## Decision

I chose to use React to develop the TrocSkillHub front-end. This choice first meets the need to build an interface as reusable components, which facilitates maintenance, visual consistency and the evolution of the application.

This choice also corresponds to a personal skills development objective. I wanted to deepen my understanding of React and better understand the logic of components, state and client-side navigation. At the same time, I had to work on a SPA application in a company project, which reinforced the interest of using React in this RNCP project in order to consolidate a skill directly applicable in a professional context.
